# ForensicShield: Evidence Provenance, Read-Only Integrity, & Extensible Architecture

## 1. Executive Summary & Legal Compliance Standards

Digital forensics tools used in law enforcement, incident response, and legal proceedings are subject to strict evidentiary standards. Under **ISO/IEC 27037:2012** (*Guidelines for identification, collection, acquisition, and preservation of digital evidence*) and **Federal Rules of Evidence Rule 902(14)** (*Self-Authenticating Records Generated by an Electronic Process or System*), digital evidence must be collected, parsed, and analyzed without altering original source media.

ForensicShield enforces an uncompromised evidence recovery design centered on three core principles:
1. **Absolute Read-Only Evidence Access**: Original evidence images are accessed exclusively via binary read-only file handles (`rb`).
2. **Dual SHA-256 Pre/Post Scan Verification**: Cryptographic SHA-256 digests are calculated before and after recovery operations. Any discrepancy triggers an instant `EVIDENCE_TAMPER_DETECTED` security alert.
3. **Complete Evidence Provenance Tracking**: Every extracted file is cryptographically hashed and tied directly to its source disk offset, source evidence hash, recovery algorithm, operator identity, and tool version string.

## 2. Why Forensic Tools Must Preserve Provenance and Avoid Modifying Evidence

### 2.1 The Risk of Evidence Contamination
In digital investigations, mounting a file system with standard operating system drivers (e.g., standard Windows/Linux automount) or running unvalidated carving tools causes silent background writes. OS kernels update access timestamps (`atime`), write journal logs (NTFS `$LogFile`, Ext4 journal), or modify unallocated cluster markers.
- **Consequence**: Any write—even a single modified byte or updated timestamp—invalidates the cryptographic integrity of the evidence, rendering it inadmissible in court and vulnerable to defense suppression motions.

### 2.2 Proof of Untouched Evidence via Pre/Post Hashing
ForensicShield resolves this risk by computing streaming SHA-256 hashes immediately before initiating a recovery scan (`pre_scan_sha256`) and immediately after completing data extraction (`post_scan_sha256`).
- If `pre_scan_sha256 == post_scan_sha256`, the system generates an audit record proving the evidence remained 100% untouched throughout analysis.
- If `pre_scan_sha256 != post_scan_sha256`, execution is immediately halted, and status is recorded as `EVIDENCE_ALTERED`.

### 2.3 Comprehensive Provenance Metadata
Exporting a deleted file without recording its origin context is insufficient for courtroom authentication. ForensicShield binds every extracted artifact to a `RecoveredArtifact` provenance record containing:
- **`artifact_id`**: Unique tracking identifier (`EVD-REC-YYYYMMDD-XXXXXX`)
- **`source_evidence_id`**: Reference ID of parent evidence image
- **`source_image_hash`**: Immutable SHA-256 of source image at time of extraction
- **`source_offset_bytes`**: Absolute byte offset of candidate data within disk image
- **`recovered_file_hash`**: Independent SHA-256 digest of extracted output file
- **`recovery_method`**: Specific adapter algorithm used (e.g., `FAT32_DELETED_CARVE`, `NTFS_MFT_PARSER`)
- **`tool_version`**: ForensicShield version string (`ForensicShield v1.0.0`)
- **`operator_username`**: Authenticated analyst who initiated extraction

## 3. Extensible Adapter Architecture

ForensicShield utilizes an extensible object-oriented adapter design (`BaseFilesystemAdapter`) to decouple recovery logic from database and REST API endpoints.

```
                  +-----------------------------------+
                  |      BaseFilesystemAdapter        |
                  |  (Abstract Interface & Contracts) |
                  +-----------------------------------+
                                    |
          +-------------------------+-------------------------+-------------------------+
          |                         |                         |                         |
          v                         v                         v                         v
+-------------------+     +-------------------+     +-------------------+     +-------------------+
| FAT32Adapter      |     | NTFSAdapter       |     | Ext4Adapter       |     | UnsupportedAdapter|
| (0xE5 Deleted Entry)|   | (MFT Record Carve)|     | (Deleted Inodes)  |     | ("Never Guess")   |
+-------------------+     +-------------------+     +-------------------+     +-------------------+
```

### 3.1 Standard Adapter Contract
All filesystem adapters inherit from `BaseFilesystemAdapter` and implement three required methods:
1. `detect(file_handle, image_size: int) -> Tuple[bool, str, Dict[str, Any]]`: Scans headers/superblocks to verify filesystem magic signatures (`0xAA55` for FAT32, `NTFS` VBR, `0xEF53` for Ext4).
2. `scan_deleted_entries(file_handle, image_size: int, check_cancelled) -> List[CandidateItem]`: Scans unallocated structures and extracts candidate records with bounds validation.
3. `extract_candidate_data(file_handle, candidate, image_size: int, output_dir: Path) -> Tuple[bool, Path, str, int]`: Safely reads data extents and exports to output directory.

### 3.2 The "Never Guess" Policy for Unsupported Filesystems
When encountering unrecognized volume structures, unknown partition tables, or corrupted filesystem headers:
- ForensicShield **never guesses** or fabricates false positive file recoveries.
- The `UnsupportedFilesystemAdapter` returns a structured candidate with status `UNSUPPORTED` and the explicit guidance:
  > `UNSUPPORTED_FILESYSTEM_MANUAL_REVIEW_REQUIRED: Target disk image does not match any supported filesystem signatures (FAT32, NTFS, EXT4) or contains corrupted volume headers. Manual analyst laboratory inspection required in accordance with ISO/IEC 27037:2012.`

## 4. Safe Bounds Validation (`OffsetBoundsValidator`)

Raw filesystem metadata (directory entries, MFT records, inode tables) can be intentionally or accidentally corrupted by attackers or hardware failures. Relying blindly on declared offset and length values can cause buffer overflows, memory exhaustion, or out-of-bounds file reads.

`OffsetBoundsValidator` enforces two strict invariant checks before any disk read operation:
1. **Range Validation**: `0 <= offset < image_size` and `length >= 0`
2. **Boundary Validation**: `offset + length <= image_size`

### Candidate Status Classification Matrix

| Status | Condition & Handling |
| :--- | :--- |
| **`RECOVERABLE`** | All data extents fall strictly within image bounds (`offset + length <= image_size`) and data clusters are intact. |
| **`PARTIALLY_RECOVERABLE`** | Extent range partially exceeds bounds or contains unallocated gap regions. Safely clamped via `safe_clamp_extent()`. |
| **`METADATA_ONLY`** | Record entry found (name, timestamps, size), but cluster pointers are wiped, zeroed out, or empty (`declared_size == 0`). |
| **`CORRUPTED`** | Offset or extent range exceeds physical image boundary (`offset >= image_size` or `offset + length > image_size`). |
| **`UNSUPPORTED`** | Filesystem format signature unrecognized or corrupted beyond automatic adapter parsing. |
